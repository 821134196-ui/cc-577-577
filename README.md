# 冷链保温箱清洗批次与门店交接系统

配送中心回收各门店的保温箱 → 安排清洗（消毒批次）→ 质检（无残留、已干燥才标为可用）→ 配送员出库 → 门店签收，全程可追踪每只箱子的处理记录与位置。

## 技术栈

- 后端：TypeScript + NestJS + Prisma（SQLite）
- 前端：React + Vite + React Router
- 扫码与通知：本地模拟（扫码 = 输入框回车；通知 = 站内通知表）

## 一键启动

```bash
npm start
```

该命令会：安装依赖 → 生成 Prisma Client → 建 SQLite 库（`backend/prisma/dev.db`）→ 写入演示种子数据 → 同时启动后端（http://localhost:3001/api）与前端（http://localhost:5173）。

之后日常启动只需 `npm run dev`。重置演示数据：`npm run seed`。

## 演示场景

浏览器打开 http://localhost:5173 ，或运行命令行演示脚本（需服务已启动）：

```bash
npm run demo
```

1. **质检不合格出库被拦截**：门店退回 BX-0001 → 清洗 → 质检不合格（清洗剂残留，退回重洗）→ 出库时被逐只拦截并说明原因；同时演示「清洗员不能质检自己的批次」（王清洗质检自己的批次会被 403 拦截）。
2. **重复箱号处理**：同一交接单中重复扫描 BX-0008 只计一次；对 SH-0001 的 BX-0012 重复签收，第二次幂等忽略，不会形成两条有效交接。
3. **跨店调拨位置变化**：BX-0008/BX-0009 从配送中心出库（在途）→ 城西店签收后位置更新为门店，上次使用门店同步更新；任一时刻一只箱只有一个有效位置。

前端操作路径：

- **退回登记**：选择门店 → 扫箱号 → 登记箱况（完好/箱体破裂/污渍残留）
- **清洗批次**：清洗员建批次 → 扫码加入「已退回」的箱子 → 完成清洗（转入待质检）
- **质检**：勾选「无残留 / 已干燥」自动判定；不合格必须填原因并选去向（退回重洗/隔离维修/报废）
- **调拨交接**：选目的门店与配送员 → 扫「可用」箱 → 出库；门店在交接单详情扫码签收或拒收
- **保温箱 → 详情**：查看上次使用门店、清洗结果、本次交接与完整事件流水

## 核心业务规则

- 质检员确认「无残留 + 已干燥」才标为可用；**未通过质检的箱子不得出库**（出库接口逐只校验状态并拦截）。
- **清洗员不能质检自己的批次**（服务端强制校验）。
- 同一箱号在调拨和签收期间**只有一个有效位置**（在途绑定交接单，签收后落到门店，事务内更新）。
- **重复扫描幂等**：批次内/交接单内同箱号唯一约束 + 签收幂等，不会多出一只箱，也不会形成两个同时有效的交接。
- 箱体破裂、清洗剂残留、门店拒收分别记录处理去向（报废 / 退回重洗 / 隔离维修 / 退回配送中心）。

## 主要 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/dashboard | 总览统计 |
| GET | /api/boxes, /api/boxes/:code | 箱子列表 / 详情（含事件流水） |
| POST | /api/returns | 门店退回登记 |
| POST | /api/wash-batches，/:id/scan，/:id/complete | 清洗批次 |
| GET/POST | /api/qc/pending，/api/qc/inspect | 质检 |
| POST | /api/shipments，/:id/sign，/:id/reject | 调拨出库 / 签收 / 拒收 |
| GET/POST | /api/notifications | 本地模拟通知 |
